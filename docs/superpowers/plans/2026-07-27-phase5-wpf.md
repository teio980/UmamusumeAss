# Phase 5 WPF Application Implementation Plan

> Execute task-by-task with test-first development and a task review after each task.

**Goal:** Deliver the WPF Log and Settings application shell specified in `docs/superpowers.md`.

**Architecture:** A `net10.0-windows10.0.17763.0` WPF application consumes the existing `Umamusume.CoreBridge` only through `IUmaService` and supplies a dispatcher-backed `IEventDispatcher`. `SettingsViewModel` owns connection configuration and state, while `LogViewModel` displays bridge events. `RootView` hosts exactly Log and Settings tabs.

**Tech stack:** WPF, C# 14, Stylet 1.3.7, HandyControls 3.6.0, xUnit 2.9.2.

## Global Constraints

- Create `docs/DESIGN.md` from the binding design system in `docs/superpowers.md` section 6 before creating XAML components.
- Preserve the Phase 4 bridge boundary. Do not change `Umamusume.CoreBridge`, C++ sources, CMake, or the C ABI.
- Use `net10.0-windows10.0.17763.0`, Stylet 1.3.7, HandyControls 3.6.0, strict nullable analysis, and warnings-as-errors.
- Use hand-written fakes, not Moq. Every behavioral production change begins with a test that fails for the missing behavior.
- Use WPF `DynamicResource` keys for every user-visible label.
- RootView contains exactly two `TabItem` entries: Log and Settings. No `ConnectView` or `ConnectViewModel` may exist.
- Settings uses a 160px left navigation with Connection, Language, and System panels.
- Task 11 creates an S2 display-only readiness card. It must remain disabled because the Phase 4 public `IUmaService` exposes no S2 control APIs.
